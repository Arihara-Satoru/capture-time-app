# 拍摄时间修正

仅供本机侧载使用的 Android 工具。应用扫描共享存储中的 JPEG、HEIC/HEIF 和 PNG，按照设置中选择的依据字段计算目标时间，并在用户明确确认后写入所选 EXIF 时间字段或文件修改时间。

应用不联网、不上传数据、不改文件名、不自动删除照片、不直接更新 MediaStore `DATE_TAKEN` 或 `DATE_ADDED`，也不访问小米图库的私有数据库或接口。只有用户在“照片重复纠正”页面明确勾选并确认后，应用才会按安全链路删除候选副本。Manifest 未声明 `INTERNET` 权限。

## 当前版本：v1.4.5

- 候选卡片将当前时间、添加时间和文件名时间分为三行完整显示，不再因两行限制隐藏文件名时间。
- 文件名解析规则更新后会自动丢弃旧扫描快照；扫描摘要新增已识别文件名时间的照片数量，确保 `mmexport` 等命名的识别结果可见。

- 修复 `mmexport1577440495004` 类文件名的 13 位 Unix 毫秒时间戳识别；相机时间后紧跟的 13 位数字副本编号不再覆盖拍摄时间或造成歧义。
- 重复照片扫描会按 MediaStore 的 EXIF 方向归一化图片宽高比，并统一 `/sdcard` 与 `/storage/emulated/0` 的路径键，避免同目录旋转照片或路径别名导致副本漏检。

- 重复清理区分已执行删除、核验通过、待确认和未删除；系统扫描超时、媒体库残留或查询失败不会误报核验通过。核验时发现原路径重新出现会提示检查同步，不会再次删除。
- 删除开始即清空旧候选，复扫失败后不再保留可操作的旧列表。
- 合入首页蓝灰配色、留白、标题与文案调整。

- EXIF 写入前检查 JPEG 元数据段长度与边界；发现此类异常时提示“JPEG 结构异常，无法写入”，在修改原件前终止并在 `skipped.tsv` 记录原因。检查覆盖首个图像扫描段之前的头部结构，不等同于完整图像解码校验，不会自动修复或重压缩照片。

### EXIF 时区偏移修复

扫描、规则计算与媒体核验会读取三个 EXIF 时间各自的 `OffsetTime*` 偏移（例如 `+09:45`）。缺少偏移时继续按 `Asia/Shanghai` 解析，非法偏移不会被猜测为本地时间。写入某个 EXIF 时间时，同步写入与输出时间配套的时区偏移；未修改字段保留原偏移。恢复检查包含原始偏移标签。升级后需重新扫描，以更新旧快照中的目标时间。

- 修复系统保留毫秒精度导致同一秒拍摄时间被误判失败的问题；扫描与核验等待各自缩短为 3 秒，恢复流程同步生效，核验截止时间包含设备休眠时间。

- 修复仅修改文件修改时间或其他 EXIF 字段时，媒体扫描将旧数据库拍摄时间刷新为已有 EXIF 原始时间，却被误判为失败并等待 15 秒后恢复的问题。现在从写入后的文件重读 EXIF 原始时间计算扫描核验预期。

- 明亮克制的 Material 3 界面，并完整适配系统深色模式；首页会明确展示本机处理与权限状态。
- 照片候选和重复项列表使用虚拟化列表，重点信息、选中状态和安全执行入口保持清晰可见。
- “清除备份”会同时处理时间纠正会话 `capture-time-app-*` 与重复清理会话 `duplicate-cleanup-*`，不会触及 `.temp` 下其它内容。

### 拍摄时间纠正性能优化

- 执行计划与未选中项目清单改为缓冲批量写入，每份清单只强制刷盘一次，避免大图库准备阶段逐行刷盘；每张实际处理结果仍独立刷盘。
- 备份、恢复与 SHA-256 使用 256 KiB 顺序读写缓冲，保留完整副本、落盘及原件/副本双向哈希校验。
- 执行弹窗显示完成数、成功数、累计用时、当前照片及处理阶段。
- 会话新增 `timings.tsv`，记录每张照片的写入前校验、备份、EXIF、系统媒体扫描、MediaStore 核验和失败恢复耗时（毫秒）。系统扫描或核验超时仍按原安全规则处理，可用此日志定位设备上的实际瓶颈。

## 环境

- Android 11（API 30）或更高版本
- Android Studio Ladybug 或更新版本
- Android SDK Platform 35
- JDK 17（Android Studio 自带的 JBR 即可）
- 小米 HyperOS 手机，系统时区设为 `Asia/Shanghai`（UTC+08:00）

## Android Studio 构建

1. 在 Android Studio 中选择 **Open**，打开本 README 所在的 `capture-time-app` 目录。
2. 等待 Gradle Sync 完成。首次构建需要 Android Studio 下载 Gradle、Android Gradle Plugin、Kotlin 插件和 `androidx.exifinterface`。
3. 选择 **Build > Build Bundle(s) / APK(s) > Build APK(s)**。
4. Debug APK 位于 `app/build/outputs/apk/debug/app-debug.apk`。

也可在已配置 JDK 17 和 Android SDK 的终端执行：

```powershell
.\gradlew.bat testDebugUnitTest
.\gradlew.bat assembleDebug
```

依赖仅来自 Google Maven/Maven Central：Android Gradle Plugin、Kotlin Gradle Plugin、`androidx.exifinterface` 和仅用于本地测试的 JUnit。应用运行时不使用任何云服务或网络 SDK。

## GitHub 自动化

- 对 `main` 的推送和所有拉取请求会运行单元测试、构建 Debug APK，并将 APK 作为 Actions 构件保留。
- 推送形如 `v1.0.0` 的版本标签会构建已签名 Release APK、生成 SHA-256 校验文件，并创建带 GitHub 自动生成发布说明的 Release。发布工作流需要仓库 Secrets 中的 `ANDROID_KEYSTORE_BASE64`、`ANDROID_KEYSTORE_PASSWORD`、`ANDROID_KEY_ALIAS` 和 `ANDROID_KEY_PASSWORD`。其中 `ANDROID_KEYSTORE_BASE64` 是发布 keystore 文件的 Base64 文本；在 Linux/macOS 可用 `base64 -w 0 release.keystore` 生成。

## 安装

1. 将 `app-debug.apk` 传到手机本地。
2. 在系统文件管理器中打开 APK。
3. 按 HyperOS 提示允许该来源安装未知应用。
4. 完成安装后打开“拍摄时间修正”。

无需 root，不需要 ADB shell。GitHub Release 的 APK 必须使用稳定的发布证书签名；首次安装和后续升级都应使用同一证书。`app-debug.apk` 仅适合开发测试，不能覆盖安装已发布版本。

## 授予权限

1. 首次打开应用时，在授权提示中点击“前往应用设置”，也可随时点击首页右上角设置按钮。
2. 在设置页的“照片访问”卡片中点击授权按钮，允许照片读取权限。
3. 随后在系统设置中打开“允许访问所有文件”。
4. 返回应用，确认页面显示“权限状态：已授予”。

拒绝或撤销 `MANAGE_EXTERNAL_STORAGE` 后，扫描和所有写入入口均禁用。每张照片真正写入前还会再次检查权限。

## 撤销权限

可使用任一方式：

- 系统设置 > 应用 > 特殊应用权限 > 所有文件访问权限 > 拍摄时间修正 > 关闭。
- 系统设置 > 应用管理 > 拍摄时间修正 > 权限，撤销照片读取权限。
- 卸载应用。

撤销权限不会删除已有会话备份和日志。

## 使用流程

1. 在首页选择一种只读入口：“从相册选择”会打开 Android 系统相册并支持多选本机照片；“全局扫描”会检查全部受支持的相册目录。两种入口都不会自动写入。
2. 查看每项的路径、当前拍摄时间、添加时间、文件名时间、目标时间、格式和安全状态。
3. 选择一张 JPEG 候选，点击“单张试运行”，阅读确认对话框后再次确认。
4. 只有 JPEG 完整通过备份、写入、EXIF 重读、媒体扫描和 MediaStore 精确验证后，批量按钮才会启用。
5. 点击“查看并批量执行”查看预计处理数、跳过数和风险，再次确认后才逐张执行。
6. HEIC/HEIF 和 PNG 默认不进入批量。对应格式必须先在当前预览中完成单张试运行；解锁仅在内存中有效，重新扫描或重启应用后失效。
7. 切换到“照片重复纠正”后点击“扫描重复项”。SHA-256 完全一致的文件会作为严格重复候选；同目录下文件名前缀与另一张图片相同、且名称中带下划线的文件也会作为命名候选。命名候选可能内容不同，默认待处理分辨率较低的一张；分辨率相同时，默认待处理字节数较小的一张；两项都相同时，默认待处理带下划线的一张。请先使用“比对”检查并可取消勾选。确认后应用会重新核验两张图各自的路径、MediaStore 有效尺寸、实际大小和 SHA-256。
8. 每批使用新的 `/sdcard/.temp/duplicate-cleanup[-debug]-日期时间/`，按原始相对路径备份；`-debug` 仅出现在 Debug 版。备份通过逐字节 `cmp` 等价校验和 SHA-256 校验后写入 `prepared.tsv`，随后由 Android 系统删除确认统一处理精确的 MediaStore URI，使系统相册和云同步收到正式删除事件。系统确认后写入 `deleted.tsv`，并核验原路径、媒体库记录、保留文件和备份文件后重新扫描。系统确认界面打开期间，MediaStore 无法提供按哈希条件删除；请及时确认，并避免同时使用其它应用替换同一路径文件。

应用未获得完整照片和视频访问权限时，每次冷启动都会显示授权说明；首页与设置页都会显示权限状态。扫描快照保存在应用私有本机空间 `files/last-scan.json`，下次打开应用会先显示上次快照；需要获取最新文件状态时可重新从相册导入或执行全局扫描。列表只显示候选项，并使用 `RecyclerView` 虚拟化滚动，不会为全部照片创建界面控件。

扫描快照包含格式版本；文件名时间解析规则更新后，旧版本快照会自动失效，避免继续显示升级前保存的空文件名时间。扫描摘要会显示本次识别到文件名时间的照片数量。

自定义导入使用 Android Photo Picker / 系统图库选择器，不会打开文件管理器。由于应用需要原地修改并备份照片，云端照片或无法解析为本机 MediaStore 文件的项目会明确跳过，不会复制后修改副本。

主页右上角“设置”可以配置完整时间规则：从所选依据字段中取最早或最晚时间，并选择要写入的目标字段。依据字段包括当前拍摄时间、三个 EXIF 时间、MediaStore 拍摄/添加时间、文件名时间和文件修改时间；可修改字段包括三个 EXIF 时间与文件修改时间。MediaStore 字段仅供读取和写入后核验，不直接修改。

设置页还可配置忽略误差，分别输入天、时、分、秒。目标时间与某个已存在的目标字段差值不超过误差时，该字段不修改；误差大于 0 且已有可靠当前拍摄时间与目标也在误差内时，缺失的目标 EXIF 字段同样忽略，照片不会仅因缺少这些字段成为候选。误差为 0、当前拍摄时间缺失或超出误差时，缺失字段仍会补写。至少需要选择一个依据字段和一个修改字段。保存后返回主页会按新规则重新扫描。默认规则与旧版本一致：取当前拍摄时间、MediaStore 添加时间、文件名时间中的最早值，写入三个 EXIF 时间和文件修改时间。

设置页的“清除备份”只处理当前安装版本创建的 `capture-time-app` 或 `duplicate-cleanup` 会话目录，并会在永久删除前显示目录数量和大致大小并要求二次确认。Debug 与正式版使用不同的目录名称，互相不会列出或删除对方的会话。拍摄时间写入或重复删除处于执行、系统确认、核验或中断恢复状态时，清除备份会被拒绝。清除操作不跟随符号链接，并会同时删除当前版本时间纠正与重复清理会话中的照片备份和日志，但不会删除 `/sdcard/.temp` 下的其他文件或目录。清除后无法依靠这些备份恢复照片。

应用只识别文件名中的：

```text
YYYY-MM-DD-HH-MM-SS
YYYYMMDD_HHMMSS
YYYYMMDD-HHMMSS
13 位 Unix 毫秒时间戳，例如 1534600669491；若它紧跟在 `IMG_YYYYMMDD_HHMMSS_` 后，则按相机副本编号处理，不覆盖前面的拍摄时间
```

无时区的格式化文件名和 EXIF 均按 `Asia/Shanghai` 严格解析；Unix 毫秒时间戳按绝对时间解析，并仅接受 2000 年至 2100 年范围内的值，避免把普通长编号误判为时间。非法日期会忽略；相机时间后紧跟的数字副本编号不会造成文件名时间歧义；其它情况下一个文件名中出现多个不同有效时间会跳过。

## 扫描范围与排除项

扫描：

```text
/sdcard/DCIM
/sdcard/Pictures
/sdcard/Download/MiShare
```

`DCIM` 大小写不敏感并去重。应用不跟随符号链接。路径任一段为 `.globalTrash`、`.thumbnails` 或以 `.trashed-` 开头时均排除；`/sdcard/DCIM/.globalTrash` 有额外硬保护。重复清理页会扫描视频，但只处理同目录 `VID_YYYYMMDD_HHMMSS` 原名与 `_六码` 后缀版本，且分辨率、时长和实际字节数必须完全一致。扫描和重复清理不会读取、清理或删除 `/sdcard/.temp` 的既有内容；仅设置页“清除备份”会删除本应用已明确识别的两类会话目录。

## 安全链路

每次单张或批量执行都会创建全新的目录：

```text
/sdcard/.temp/capture-time-app[-debug]-YYYYMMDD-HHMMSS/
```

其中 `-debug` 仅出现在 Debug 版；正式版沿用不带该段的历史目录格式。

每张照片按相对原路径备份。应用要求备份和原文件长度及 SHA-256 完全一致，才使用 `ExifInterface` 写入用户勾选的一个或多个字段：

```text
DateTimeOriginal
DateTimeDigitized
DateTime
```

写入值格式为 `yyyy:MM:dd HH:mm:ss`。应用不解码、重编码或压缩像素。写入后立即重读所选标签并核验所选文件修改时间，再调用公开的 `MediaScannerConnection.scanFile()`。扫描回调等待与 MediaStore 核验轮询各自设为 3 秒，恢复流程也使用此上限。轮询使用包含设备休眠时间的单调时钟计时；系统查询阻塞或进程暂停仍可能让实际墙钟耗时超出上限。

存在有效 `DateTimeOriginal` 时，要求 `DATE_TAKEN` 与它落在同一秒内，无论该字段本次是否修改，允许系统保留 EXIF 亚秒精度；跨秒不视为匹配。没有可解析的 EXIF 原始时间时回退到原 MediaStore 拍摄时间并精确比较毫秒（原值也缺失时不核验该列）。恢复核验仍精确比较原数据库毫秒值；操作前后的 `DATE_ADDED` 秒值始终必须完全一致。

缺少可查询 `DATE_ADDED` 的文件会跳过，因为应用无法安全证明添加时间未变化。应用从不直接更新 MediaStore 时间列。

任何写入后错误都会立即从本会话备份覆盖恢复原文件，校验恢复文件与备份 SHA-256 一致，重新扫描，并核验原 EXIF、原 `DATE_TAKEN` 和原 `DATE_ADDED`。没有无限重试。若进程在写入、恢复或日志落盘期间中断，下次启动会保留恢复状态锁，禁止新的写入、重复删除和备份清理；用户检查原文件和对应会话备份后，必须明确确认才会仅解除该状态锁，解除操作不会删除照片或备份。

## 日志

每个会话目录包含：

- `planned.tsv`：该次执行采用的完整扫描快照、候选与跳过原因。
- `changed.tsv`：成功修改及 EXIF、MediaStore 核验结果。
- `skipped.tsv`：未修改项目及原因。
- `restored.tsv`：写入后失败并进入恢复流程的项目、恢复核验结果。
- `summary.json`：扫描、候选、成功、跳过、恢复、失败计数和会话路径。

重复清理会话目录包含 `deleted.tsv`，列为 `original_path`、`retained_path`、`backup_path`、`confirmation`。该清单在观察到原路径消失后写入，不代表媒体库核验通过，也不能单独证明文件消失由本次请求导致；`confirmed` 表示应用已收到系统确认成功结果，`unknown` 表示进程或 Activity 中断后由用户发起只读核验。删除后的扫描、核验或日志错误单独显示为待确认，不再算作未删除；删除前失败不会删除原件。文件删除和日志写入之间仍有断电窗口。既有 `capture-time-app-*` 备份不会被重复清理功能删除。核验只保证检查时的状态，不能阻止外部云相册后续重新下载。

日志为 UTF-8。首页“查看最近会话日志”可查看摘要和目录；也可用系统文件管理器打开该目录。

## 手工恢复

正常失败会自动恢复。若手机断电、系统强杀进程或存储故障导致自动恢复没有完成：

1. 立即停止使用应用，不要再次对同一照片执行批量操作。
2. 打开最近的会话目录，根据 `restored.tsv`、`changed.tsv` 和 `summary.json` 找到原路径与 `backup_path`。
3. 备份目录保持了原共享存储相对路径，例如会话中的 `DCIM/Camera/IMG_0001.jpg` 对应 `/sdcard/DCIM/Camera/IMG_0001.jpg`。
4. 先将当前原路径文件另存到其他位置，再将会话备份复制回原路径。不要改名。
5. 在系统设置中重启媒体存储相关服务或重启手机，让系统重新扫描；不要手工编辑 MediaStore 数据库。
6. 比较恢复文件和会话备份的 SHA-256；只有完全一致才视为文件内容恢复。

应用从不自动删除会话目录。确认无需恢复后，用户可在设置中清除 `capture-time-app-*` 与 `duplicate-cleanup-*` 会话，或自行归档或删除特定目录；不要让清理工具误删尚需恢复的备份。

## 平台限制

- 小米图库是否立即刷新由 HyperOS 媒体扫描器决定；应用以公开 MediaStore 的精确核验为成功条件。
- HEIC/HEIF、PNG 的可写能力取决于设备、系统版本和具体文件结构，因此必须逐格式完成当前预览的真实单张测试。
- 系统媒体提供程序若自行改变 `DATE_ADDED`，应用会判定失败并恢复照片内容，但不会违反约束去写回该数据库列。
- 应用只能防护自身进程内可检测的错误。断电和底层存储损坏无法做到绝对事务原子性，因此原始备份会永久保留，直到用户自行处理。
